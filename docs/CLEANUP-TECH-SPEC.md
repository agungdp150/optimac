# Cleanup coverage and disk reclamation

Status: proposed implementation specification; initial read-only inventory slice implemented, full Phase 1 pending. Research date: 2026-11-11.
Scope: macOS Rust edition, currently 0.2.0. This document authorizes no cleanup. See README Storage inventory for the implemented slice and remaining work.

OptiMac needs broader inventory and a real reclamation workflow. The initial release inventories broadly, keeps all selections off, and enables mutation only after each adapter passes its certification gate. Moving to recovery never counts as reclaimed storage.

Read the normative [adapter implementation contract](CLEANUP-ADAPTER-CONTRACT.md) for executable trust, activity evidence, version gates, reconciliation, recovery lifecycle and schema semantics. The complete user-overlay appendix is [rules.example.toml](rules.example.toml). The contract refines the proposals below; unverified adapter capabilities remain disabled.

## Problem and evidence

The user reports roughly 20 GB reclaimed by another tool versus roughly 2 GB shown by OptiMac. We have not measured those runs or identified the other tool's categories, so the exact difference remains unverified.

Source inspection provides concrete explanations:

- `src/recovery/mod.rs::cache_roots` lists only five developer locations and five browser locations. Homebrew, Yarn, Poetry, Gradle, CocoaPods, Composer, Xcode, Docker, Trash and application caches have no dedicated providers.
- `preview` accepts regular files with modification times at least 30 days old. It excludes symlinks, multiple hard links and files not owned by the current user. Age alone does not establish disposability or last use.
- `src/common/limits.rs` limits cleanup to 10,000 visited entries, depth 16 and 15 seconds across all roots. A large early cache can consume the budget before later roots are inspected.
- The fixed pip path is `~/.cache/pip`; pip documents `~/Library/Caches/pip` as the macOS default and offers `pip cache dir` for configuration-aware discovery. Go also exposes its actual build and module cache locations through `go env`. [pip caching](https://pip.pypa.io/en/stable/topics/caching/), [Go installation management](https://go.dev/doc/manage-install).
- `execute_with_progress` moves files into `~/.optimac-rust-recovery` on the same filesystem. It never permanently deletes them. Individual regular-file recovery purge is now available; directory and bulk purge remain pending. Its displayed totals use logical lengths, not physically reclaimed bytes.
- `src/common/categories.rs` groups content into categories such as Programming and Documents. Those labels do not explain why an item can be removed.
- `src/actions/process.rs` now provides a structured runner with separate bounded streams, retained timeout output and caller-selected deadlines. The legacy text wrapper remains for diagnostics. Executable trust, adapter certification and postcondition reconciliation remain required before native cleanup.

The first improvement must make deletion semantics and accounting truthful. Expanding paths alone will move more data without reclaiming storage.

## Product decisions

1. Clean becomes a provider-based review of disposable caches and generated outputs. Personal documents stay in Analyze and retain explicit recovery-based removal.
2. Show every supported provider as complete, partial, unavailable, permission denied, blocked, or unsupported version. Missing data is never presented as zero bytes.
3. Offer three distinct operations: **Move to recovery**, **Delete permanently**, and **Open tool instructions**. Native cleanup commands are permanent unless proven otherwise. Never silently change modes.
4. Keep backups, archives, simulator resets and stopped-container removal in an **Advanced review** section, with no automatic selection.
5. Do not promise 20 GB. Success means complete eligible coverage and an honest account of observed filesystem change.
6. Memory remains a diagnostic feature. Apple describes cached memory as part of memory management and pressure assessment; this proposal excludes RAM purge, swap deletion and claims that free RAM equals disk cleanup. [Activity Monitor](https://support.apple.com/en-gb/guide/activity-monitor/actmntr1004/10.14/mac/15.0).

## Eligibility policy

These thresholds are proposed OptiMac defaults, not vendor recommendations. Discovery includes recent items so the user can see what was excluded.

| Class                  | Criteria                                                                                                  | Default selection                                                                                               | Effect                                         |
| ---------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Rebuildable cache      | Verified provider and supported version; validated resolved root; provider idle; known regeneration route | Off; suggest entries unused for 30 days when reliable last-use evidence exists; otherwise individually reviewed | Downloads or rebuilds may be required          |
| Generated build output | Identified project/output relationship; source remains; no active build                                   | Off; suggest inactive projects after 90 days and 100 MB aggregate size, with evidence and unknown-age label     | Next build/indexing takes longer               |
| Logs                   | Known application log schema; rotated, closed, user-owned; older than 30 days                             | Off initially                                                                                                   | Diagnostic history is lost                     |
| Recovery / Trash       | Exact selected item already in a validated local holding directory                                        | Off; explicit permanent-delete confirmation                                                                     | Restoration through OptiMac becomes impossible |
| User state             | Backup, archive, emulator data, container writable layer, game data                                       | Off; dedicated review or vendor UI                                                                              | May be irreplaceable                           |
| Unknown content        | Unsupported schema, active/unknown owner state, denied access, incomplete inventory                       | Never                                                                                                           | Report why blocked                             |

Never apply a 30-day filter to a whole-cache native command and imply that recent entries will survive. Whole-cache purge must be a separately selected action whose review states its full scope. Do not equate mtime, creation time, and last use. Unknown age stays unknown.

### Docker

Discover the active Docker context and daemon identity first. Only a verified local Docker Desktop endpoint is eligible initially; remote or ambiguous contexts are read-only. Use `docker system df -v` plus object inventory. Keep dangling images, stopped containers and build cache as separate categories. Docker documents these distinct objects and prune behavior. [Docker pruning](https://docs.docker.com/engine/manage-resources/pruning/).

For exact selection, prefer removal of reviewed image/container IDs without force, after rechecking their state. Stopped containers are user state because their writable layers can contain unique work. Never include volumes, networks, running containers, tagged unused images or `docker system prune` implicitly. Build-cache pruning is deferred until its scope and concurrent-builder behavior can be represented accurately.

Report daemon-reported bytes separately from host disk change. Docker Desktop may return disk space asynchronously, and virtual disk logical capacity is not allocated host storage. Never remove or truncate Docker's virtual disk file. [Docker Desktop disk accounting](https://docs.docker.com/desktop/troubleshoot-and-support/faqs/macfaqs/).

## Inventory executable policy

Read-only inventory may probe fixed absolute executable candidates without full enrollment after refusing final-component symlinks and files or ancestors writable by other users. Environment and supported configuration take precedence; subprocesses use bounded output, explicit environment and a neutral directory, without PATH search, shell, network or automatic installation. These checks are a lightweight inventory policy, not executable authentication. Full executable trust enrollment and the adapter contract are required before Step 3 can enable new deletion operations.

## Architecture

Introduce `src/cleanup/` with `provider.rs`, `policy.rs`, `plan.rs`, `accounting.rs`, `executor.rs`, `journal.rs` and `providers/`. Reuse hardened filesystem primitives from recovery, but do not reuse file-category labels as authorization.

Provider lifecycle: `probe -> discover -> assess -> plan -> revalidate -> execute -> reconcile -> measure`. Each stage returns structured errors and completeness. Discovery has no deletion side effects and never launches an installer, project hook or automatic update.

Each provider definition contains an ID, policy version, supported tool versions, discovery method, root constraints, exclusions, regeneration explanation, activity/lock checks, operation scope, source URLs and verification date. Rules ship with releases; remote text cannot introduce executable rules.

An immutable plan records:

- Plan ID/hash, schema version, creation/expiry time, provider/policy/tool versions and executable identity.
- Target paths or object IDs, root identity, volume identity, owner, inode, type, size and high-resolution modification/change timestamps where supported.
- Operation type: recovery move, permanent file removal, exact native-object removal, whole-tool purge, or guided action.
- Eligibility evidence, age evidence, exclusions, app state, loss/rebuild consequences and restore availability.
- Logical bytes, allocated-byte estimate, unknown/shared allocation flag and scan completeness.
- Ordered arguments, controlled environment, neutral working directory, timeout and reconciliation strategy for native operations.

Proposed plan validity: ten minutes maximum; every target must still be revalidated immediately before mutation. Expiration is not the safety boundary. Changed provider scope or changed whole-tool inventory requires a refreshed review. Native tools without atomic preview guarantees must be labeled as tool-managed scope and remain opt-in; do not present them as an exact file transaction.

### Filesystem execution and recovery

Keep root refusal, ownership checks, no-follow traversal, same-volume constraints and exclusive rename. Add descriptor-relative recursive enumeration/removal with identity checks; path-based `remove_dir_all` is not the authorization boundary. Reject traversal escapes, mount changes, cloud placeholders, symlinks and hard-linked content in the initial deletion engine. Never follow exclusions into a descendant subtree.

For direct permanent removal, first move the exact validated unit into a private same-volume operation staging directory, verify identity, then delete its approved contents through directory descriptors. This is temporary staging, not a promise of recovery after deletion begins. New/changed descendants stop that unit; never broaden the plan. Journals and staging cannot live inside a target root. No copy-delete fallback across volumes.

Persist states `planned`, `validated`, `staged`, `deleting`, `completed`, `skipped`, `failed`, `cancelled`, `needs_reconciliation`. Sync intent before mutation and completion afterward. On restart, reconcile staged payloads and tool state; never replay a destructive native command automatically. Partial deletion cannot be rolled back. Keep old recovery records readable; add new journal versions instead of rewriting history.

Activity detection is three-state: active, idle, unknown. Unknown blocks direct mutation. Process-name matching and lsof alone cannot guarantee absence of races; adapters need tool locks where available and conservative refusal otherwise. Do not stop applications automatically.

### Command execution

Return stdout, stderr, exit status, duration, timeout/cancellation state and truncation flags separately. Use direct argument arrays, validated executable paths, controlled environment and no shell interpolation. No network bootstrap, Corepack download, shell startup script or arbitrary project executable during probing. Neutral working directories prevent accidental project configuration/plugin execution; providers must document intentional configuration resolution.

Read-only probes may retain short timeouts. Mutation deadlines are provider-specific; cancellation stops scheduling new operations and requests graceful termination before escalation. A killed native command yields unknown/partial completion until reconciled. Preserve bounded output and progress. Never infer success solely from exit code or a printed byte count.

## Scan performance and accounting

Use metadata-only scans with at most two workers initially. Schedule roots fairly, report progress per provider, and offer Quick and Deep scans. Proposed Quick budget: 10,000 entries or two seconds per provider, 30 seconds globally. Proposed Deep budget: 250,000 entries per provider, 1,000,000 globally, two minutes globally, explicitly extensible by the user. These are bounded starting points to benchmark, not measured performance claims. Partial scans cannot authorize whole-tree deletion.

Deduplicate overlapping provider roots and `(device, inode)` identities. Logical size is content length; allocated size derives from filesystem allocation metadata, with directory metadata and shared/cloned extents treated carefully. APFS clones and snapshots prevent allocated totals from being guaranteed savings. Never sum per-provider free-space deltas from overlapping samples.

Before and after the batch, sample available bytes on each affected volume using `statfs`, with `f_bavail * f_bsize` as the user-available byte metric and stable volume identity. Record timestamps and signed deltas; background activity may increase or decrease them. Label this **Observed available-space change**, not exact causal bytes freed. Show provider-reported reclaimed bytes separately. Allow a bounded follow-up sample for delayed Docker reclamation without forcing sync, purge or snapshot deletion.

Example result labels, with illustrative values only:

```text
Selected content:              12.4 GB logical
Estimated allocated storage:   10.1 GB (shared storage uncertain)
Deleted content:                8.0 GB logical
Moved to recovery:              1.0 GB (no immediate space reclaimed)
Observed available-space change: +6.2 GB on Data volume
Skipped: 4 items in use; 1 provider incomplete
```

## Interface and compatibility

Clean opens a provider summary: name, discovered size, selected size, policy, effect and status. Detail view shows exact targets or explicitly whole-tool scope, reasons, last-use uncertainty, rebuild cost and exclusions. Recommendations can be selected as a group only when eligibility is established. Advanced actions never inherit that selection.

Final review separates recoverable moves from permanent actions. Show a prominent permanent-delete confirmation with default Cancel; high-risk state destruction requires selecting the named object and confirming its consequence. Do not use one ambiguous Clean button for mixed semantics. Results persist per item/provider and remain visible after partial failure.

Keep existing `optimac clean` read-only. Proposed additive CLI: `clean scan --json`, `clean plan`, `clean apply <plan-id>` with interactive confirmation, and `recovery purge <id>` with explicit permanent confirmation. Noninteractive apply and unattended schedules are outside the first release. JSON includes a schema version and completeness; exit codes distinguish complete success, partial outcome, invalid usage and blocked/error conditions.

## Comparison protocol and remaining questions

To investigate the reported 20 GB versus 2 GB, collect a read-only category inventory before either tool cleans. Record tool/version, scope, exclusions, logical versus allocated estimates, actual per-volume free-space samples and categories removed. Compare equivalent restored fixtures or independent equivalent environments; running the second cleaner after the first is not a fair comparison. Record cache regrowth after a representative development session as well as immediate savings.

### Configuration and exclusion semantics

The example uses provider IDs rather than executable path globs. Built-in adapters own filesystem and tool semantics. User configuration can choose supported operations, restrict scope, raise age/size thresholds, add exclusions and disable providers; it cannot override protected roots, introduce shell commands, authorize sudo, or bypass confirmation. User project roots are explicit and initially empty.

Apply size thresholds to each review unit or aggregate cache group, not each tiny cache file. This avoids hiding a large cache made of small files. Age fields declare the timestamp basis. A complete tree inventory uses the newest relevant descendant modification time as a conservative activity hint; unknown or incomplete trees cannot qualify for automatic recommendation. Thresholds remain suggestions, not proof of safety.

Deny rules win over allow rules. Resolve current-user home without a shell; validate root and every ancestor, apply exclusions to descendants, never follow symlinks, and reject elevated execution. Skip cloud/network roots by default. Locked, open, active or unknown-state targets remain blocked even if a user rule includes them.

Protect Keychains, Photos libraries, Mail, Messages, Notes, app databases, credentials, SIP-managed locations and signed app internals. Do not strip language resources or architectures from app bundles. App uninstall remains a separate reviewed operation. System caches and `/private/var/folders` have no generic cleanup provider.

Default direct-file removal remains recoverable through OptiMac recovery. Finder Trash may be a future backend after restore/volume/permission behavior is verified; moving to either location does not immediately free space. Permanent removal needs an explicit operation choice and confirmation; a future CLI flag alone must not bypass those gates. Native purge commands that cannot offer recovery must disclose that before selection.

Evaluate `walkdir` for bounded discovery before adding `jwalk` or `rayon`; parallel traversal must obey shared I/O budgets. None provides the deletion safety boundary. Evaluate `dirs` for standard user locations, while tool-specific configuration remains authoritative. `sysinfo` can supplement process inventory but cannot prove file inactivity. The `trash` crate requires macOS integration tests before adoption. Reuse serde and evaluate `toml` for a strict schema that rejects unknown fields, duplicate IDs and invalid thresholds. No dependency is added by this proposal.

Phase 1 gains the full catalog and read-only project artifact discovery. Phase 3 gains verified Cargo/SwiftPM/Conda adapters and reviewed project cleanup; Maven remains conservative. Phase 5 gains version-specific browser/app adapters. Add tests for protected-root override attempts, excluded descendants, tracked project outputs, directory-mtime false positives, Conda linked environments, local-only Maven artifacts, and duplicate hash matches followed by file changes.

## Coverage and schema revision (review feedback)

### Broad application-cache inventory

Add `app-user-caches` for immediate child directories of `~/Library/Caches`. Inventory the long tail by descending allocated-size estimate, with logical size and incomplete counts also visible. Exclude `com.apple.*` by default. A directory name resembling a bundle ID is attribution evidence only; unrecognized names remain visible as unknown owners. This is class `unknown_content`, risk `review`, with inventory as its initial operation and no automatic selection. Attribution can route a subtree to a certified specific adapter, but never unlocks generic mutation; it does not hide the inventory.

Add separate inventory-only `sandbox-app-caches` and `group-container-caches` providers. Enumerate only `~/Library/Containers/*/Data/Library/Caches` and recognized cache-relative directories beneath `~/Library/Group Containers` (initial candidates: `Library/Caches` and `Data/Library/Caches`). These are adapter-owned patterns, not shell globs. Never inventory a whole container as disposable. Exclude Apple-owned containers/groups by resolved identity, including `group.com.apple.*`; ownership ambiguity remains blocked for mutation. Group containers can have several owning applications: all must be idle. Metadata discovery must not open databases or trigger cloud downloads.

Specific validated providers take precedence over generic inventory for the same subtree. Generic inventory displays the owning provider instead of double-counting or bypassing a stricter rule. Recovery is the default for eligible direct-file moves; unavailable/unknown activity and partial descendants block moves. Add overlap and shared-owner tests. These additions may explain missing coverage, but their contribution to the reported space gap has not been measured.

### Access preflight

Before the first Clean scan, and after changing scope or retrying permissions, perform bounded metadata/enumeration probes on enabled provider roots. Report each as readable, absent, denied or unknown. A readable parent does not imply readable descendants; continue recording scan-time denials. Do not read unrelated Mail or Messages data as a permission sentinel. Do not treat EPERM/EACCES as proof of missing Full Disk Access: ACLs, ownership, sandbox restrictions and other privacy controls may also apply.

Show a persistent summary such as “18 providers readable; 3 partially inaccessible; 2 not installed.” Denied bytes are unknown, never zero. Explain which paths/providers are affected and offer Continue with limited coverage, Retry, or permission instructions. For applicable denials, guide the user to System Settings > Privacy & Security > Full Disk Access and identify the launching terminal/app or packaged executable as appropriate; advise restarting that host and retrying. Do not request FDA for unrelated operations or require it when selected roots are already readable. Never modify TCC databases, invoke sudo, or claim a single global FDA boolean proves complete access. macOS version and launch context must be part of the compatibility test matrix. Apple requires user action to grant access; not every container universally requires FDA. [Apple filesystem access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox).

### macOS storage metrics

Use `statfs` at the actual affected volume mount: record `f_bavail * f_bsize`, `f_bfree * f_bsize`, volume identity and timestamp. The primary before/after delta is the first metric; do not mix it with Finder's displayed available capacity. Shared APFS container capacity must not be summed across sibling volumes.

Phase 1 is statfs-only. Phase 2 adds the in-process objc2-foundation bridge after the adapter contract gates pass; then query Foundation URL resource values on that volume: `volumeAvailableCapacityKey`, `volumeAvailableCapacityForImportantUsageKey`, and `volumeAvailableCapacityForOpportunisticUsageKey`. Show important-usage capacity separately because it may include storage macOS can reclaim. These are policy-dependent capacity estimates, not an exact inventory of purgeable files. Do not label the difference between APIs as measured purgeable space or add it to deletion savings. Display **Purgeable storage: not independently quantified** when no validated public exact metric is available, alongside **Available for important usage (OS estimate)**. Nil/error values remain unavailable. A future approximation must be explicitly labeled and independently validated. [Apple available capacity](https://developer.apple.com/documentation/foundation/urlresourcekey/volumeavailablecapacitykey), [important-usage capacity](https://developer.apple.com/documentation/foundation/urlresourcekey/volumeavailablecapacityforimportantusagekey).

Do not purge snapshots or OS caches to reconcile Finder numbers. Record required-reason API/privacy-manifest obligations for the eventual packaged implementation; verify the applicable API and distribution requirements during implementation.

### Normative schema and consistent defaults

Schema version 2 supersedes the initial example. Project artifacts use **90 days / 100,000,000 bytes** everywhere. `auto_select = false` applies to every class and rule in the initial release; age-based suggestions never preselect items. All example rules remain `enabled = false`.

`class` describes content; `risk` describes handling:

| Class value         | Permitted risk                  | Meaning                                                                       |
| ------------------- | ------------------------------- | ----------------------------------------------------------------------------- |
| `rebuildable_cache` | `conditional_cache` or `review` | Regeneration known; review required when provenance/cost/sharing is uncertain |
| `generated_output`  | `conditional_cache` or `review` | Rebuild evidence required; project artifacts remain review                    |
| `logs`              | `review`                        | Diagnostic data loss                                                          |
| `holding_area`      | `review`                        | Trash/recovery; permanent removal loses restoration                           |
| `user_state`        | `review` or `protected`         | Installed versions, models with unknown provenance, backups and similar state |
| `unknown_content`   | `review` or `protected`         | Inventory only until assessed; recovery proposal is not approval              |

`protected` always forbids mutation regardless of class. Validate this mapping rather than inferring class from risk.

`operation` is one of `inventory`, `recovery`, `permanent`, `guidance`. Inventory only measures; recovery proposes a recoverable move; permanent proposes irreversible filesystem/native cleanup; guidance displays vendor instructions without executing them. A permanent selection never grants unattended authorization. Each built-in provider exposes a versioned capability set; requested operations outside that set are rejected. The sample declares intended contracts, not existing runtime support. Guidance-only providers have `operation = "guidance"`; no unsupported fallback to deletion.

Global `[scope]` has `project_roots`, `file_roots`, `exclude_paths`. Per-rule `scope` is `provider`, `projects`, or `files`; `scan_roots = []` inherits the corresponding explicit global roots for projects/files, while provider scope resolves only validated provider roots. An empty effective projects/files scope means no scan, never the home directory by default. Nonempty per-rule roots must be within the corresponding global user-approved roots; provider overrides must also meet adapter constraints. `exclude_paths` merges global and local exclusions; neither can undo built-in protection. `exclude_name_patterns` applies only to basename components using documented glob matching, never shell expansion. Overlaps are deduplicated before accounting.

Per-rule `[rule.docker]` specifies `context = "current"` (or explicit name), `endpoint_policy = "local_desktop_only"`, `allow_remote = false`. Resolve environment overrides as well as CLI context and pin daemon identity in the plan. A Unix socket alone does not prove locality; verify supported Docker Desktop identity. Ambiguous/proxied or remote endpoints block mutation. Recheck context and identity at execution; a config field cannot attest locality by itself.

Add validation cases for invalid risk/class pairs, unknown operations, guidance-provider mutation requests, protected-rule mutation requests, missing file scopes, per-rule exclusions, out-of-scope roots, remote/context swaps, partial access and unavailable capacity estimates. No runtime dependency or cleanup behavior changes in this revision.
