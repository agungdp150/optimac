# Preselect only what owners can regenerate

A macOS cleanup tool can safely preselect only a narrow band of items. The band is: third-party folders in `~/Library/Caches` whose owning app is not running, ordinary app logs, the user's own Trash, Xcode DerivedData (with Xcode quit), and developer package caches cleared through the owning tool's own command (`brew cleanup`, `npm cache clean --force`, `pip cache purge`, `go clean -cache`, `uv cache prune`, `cypress cache prune`, Cargo's extracted sources). Anything that can hold the only copy of user data should at most be suggested, and much of it should never be touched. That includes `~/Library/Containers`, Group Containers, Application Support, iOS backups, Xcode Archives, Mail, Messages and Photos stores, iCloud Drive and `~/Library/CloudStorage`, Docker's disk image, and the Maven local repository. This is close to what Apple itself does. Storage settings offer the user browsing and deletion, never preselection, of Downloads, backups and apps. macOS already clears "caches and logs that are safe to delete" on its own. Howard Oakley's testing shows that cache flushing frees "considerably less" than tools report. So the preselected tier is low in value, and the tool must label its size honestly rather than market it. Root access unlocks little worth taking. The correct elevation for a terminal tool is macOS's own `sudo` prompt on a fixed command line, or `SMAppService` for a bundled app. A password field inside the app is wrong: it matches the 2025–2026 macOS stealer pattern and the CWE-522/256 credential weaknesses. For duplicates, APFS clones, hard links and dataless iCloud placeholders mean deleting a "duplicate" can free zero bytes or delete the cloud copy on every device. Auto-selection must therefore read `ATTR_CMNEXT_PRIVATESIZE`, `CLONEID` and `SF_DATALESS`, and select only exact copies in Downloads or Desktop, which is the line MacPaw's Gemini 2 draws. A restorable recovery folder meets Oakley's long-standing demand that cleaning be reversible. That protection does not cover the owner-command prunes, which delete permanently, or the cache folders that uv explicitly forbids anyone to move.

*How the evidence is labelled: claims carry inline source links. These tags mark weaker support: **[vendor]** = a cleaner vendor's own help or marketing page; **[forum]** = Apple Community, MacRumors, Apple Developer Forums or similar; **[single source]** = only one source found; **[local observation]** = a man page, SDK header, `--help` output or `ls` result read on the research machine (macOS 26.6.2 / Darwin 25.6, Xcode 27.2), which has no web URL; **[archived 2018]** = Apple's legacy* File System Programming Guide*, last updated 2018-04-09; **[snippet]** = taken from a search-result summary, not a full page read.*

## Apple calls only Caches and temp files discardable

Apple's current Foundation reference describes `~/Library/Caches` in one line as **"Discardable cache files"** ([Apple Developer: cachesDirectory](https://developer.apple.com/documentation/foundation/filemanager/searchpathdirectory/cachesdirectory)). Its iCloud Backup guidance defines purgeable data as "app data that the system can delete without affecting the app's execution and that the app can re-create if it needs" and names `/tmp` and `/Library/Caches` as the two purgeable directories ([Apple Developer: Optimizing Your App's Data for iCloud Backup](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup)). That page is written for the app container and is iOS-flavoured. The macOS-specific contract is older and softer: caches hold "data that can be regenerated as needed. **Apps should never rely on the existence of cache files**" ([File System Programming Guide: macOS Library Directory Details](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/MacOSXDirectories/MacOSXDirectories.html)) **[archived 2018]**. Apple's stronger promise, that the system purges Caches and never while the app runs, is stated only for iOS ([File System Basics](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)) **[archived 2018]**. So `~/Library/Caches/<bundle-id>` is the best-founded preselection target on macOS. Even so, it rests on a convention that badly behaved apps can break, not on a system guarantee.

Every other `~/Library` area Apple describes as app data. Application Support "can include files that contain user data" ([macOS Library Directory Details](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/MacOSXDirectories/MacOSXDirectories.html)) **[archived 2018]**. Apple itself keeps iPhone and iPad backups in `~/Library/Application Support/MobileSync/Backup/` ([Apple Support 108809](https://support.apple.com/en-us/108809)). A sandboxed app's container in `~/Library/Containers` is its entire file system, with "full read and write access". Since macOS 14 the container is tied to the app's code signature, and another app that touches it triggers a consent prompt ([Apple Developer: Accessing files from the macOS App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)). For Group Containers Apple says plainly that on macOS the system **"creates this directory automatically the first time your app needs it and never removes it,"** whereas on iOS it removes the directory with the last app in the group ([Apple Developer: containerURL(forSecurityApplicationGroupIdentifier:)](https://developer.apple.com/documentation/foundation/filemanager/containerurl(forsecurityapplicationgroupidentifier:))). Orphaned Group Containers therefore pile up by design. Apple deliberately declines to decide when they are safe to remove, and a cleaner should not presume to decide either.

The per-user directories under `/private/var/folders` behave differently from one another. According to `confstr(3)`, files in `DARWIN_USER_TEMP_DIR` (`…/T/`) "may be cleaned (removed) by the system if they are not accessed in 3 days." `DARWIN_USER_CACHE_DIR` (`…/C/`) "will not be automatically cleaned by the system" but is "removed during safe boot" **[local observation: `man 3 confstr`]**. Apple's user-facing mechanism for flushing them is a safe-mode restart, which "clears certain system caches, which are automatically created again as needed" ([Apple Support 102624](https://support.apple.com/en-us/102624)).

Apple's Storage guidance sets the baseline a preselecting tool should be measured against. macOS Tahoe 26 already "clears caches and logs that are safe to delete, including temporary database files, interrupted downloads, staged macOS and app updates, Safari website data, and more" when space is needed ([Mac User Guide 26: Optimize storage space](https://support.apple.com/en-us/guide/mac-help/sysp4ee93ca4/26/mac/26)). It calls System Data a category users **"can't manage… The contents are managed by macOS"** ([Mac User Guide 26: Find and delete files](https://support.apple.com/guide/mac-help/find-and-delete-files-on-your-mac-syspf5a64aa6/26/mac/26)). The three recommendations Apple automates are Store in iCloud, Optimize Storage, and Empty Trash after 30 days, and all three are opt-in. For Downloads, old device backups, unused apps and re-downloadable media, Apple only tells users to "Delete files in your Downloads folder" and that "you can delete old backups" ([Apple Support 102624](https://support.apple.com/en-us/102624)). **Apple never preselects user content.** A tool that does is more aggressive than macOS itself.

Apple's specific warnings mark several items as irreplaceable. For device backups: **"After you delete a backup, you can't recover it. If you want to keep a backup, archive it so that later backups don't replace it,"** and deletion goes through Finder's Manage Backups ([Apple Support 108809](https://support.apple.com/en-us/108809)). For Xcode: **"You must retain the Xcode archive for each build of your app you distribute"**, because without it "you might not be able to diagnose an issue from crash reports" ([Apple Developer: Building your app to include debugging information](https://developer.apple.com/documentation/xcode/building-your-app-to-include-debugging-information)). Simulator runtimes and platforms are removed in Xcode > Settings > Components ([Apple Developer: Downloading and installing additional Xcode components](https://developer.apple.com/documentation/xcode/downloading-and-installing-additional-xcode-components)). For crash reports (`.crash`/`.ips` in DiagnosticReports), Apple's only documentation is about finding them in Console and sending them to developers, who rely on users to supply them ([Apple Developer: Acquiring crash reports and diagnostic logs](https://developer.apple.com/documentation/xcode/acquiring-crash-reports-and-diagnostic-logs)). Deleting them costs troubleshooting evidence, not system function. Local Time Machine snapshots count as available space, and Apple says **"You don't need to think about how much storage space local snapshots are using."** Time Machine deletes them after 24 hours or when space is needed. They are also the user's fallback restore point, including the snapshot taken before each macOS update ([Apple Support 102154](https://support.apple.com/en-us/102154)).

Apple's documentation is silent on some items. No Apple source describes `~/Library/Saved Application State` or whether deleting it is safe, and the archived Library directory table does not list it ([macOS Library Directory Details](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/MacOSXDirectories/MacOSXDirectories.html)). No Apple reference page covers DerivedData or `iOS DeviceSupport`, and no page names `.dmg`/`.pkg` installer cleanup specifically. One useful public signal is that Foundation has exposed `URLResourceKey.isPurgeableKey` since macOS 11, "whether the file system can delete a file when the system needs to free space" ([Apple Developer: isPurgeableKey](https://developer.apple.com/documentation/foundation/urlresourcekey/ispurgeablekey)). A file macOS already treats as purgeable is already counted in "available" space ([Mac User Guide 26](https://support.apple.com/guide/mac-help/find-and-delete-files-on-your-mac-syspf5a64aa6/26/mac/26)). Deleting it inflates a "space freed" figure without giving the user any new capacity. The purging engine itself, the `deleted` daemon and CacheDelete, is "not intended to be invoked directly" and is a private framework **[local observation: `man 8 deleted`]**.

## Reputable tools preselect regenerable junk and leave user content to review

The cleanup tools that document their defaults converge on two tiers, and the reported incidents cluster in the tier they leave to review. MacPaw's current CleanMyMac selects every Smart Care task by default. Its Cleanup tile "automatically selects" system junk ("log files, cache files, and broken login items"), mail attachments and Trash. Its My Clutter tile scans only "duplicate files in your Downloads folder" ([MacPaw: Smart Care](https://macpaw.com/support/cleanmymac/knowledgebase/smart-care)) **[vendor]**. MacPaw says Cleanup "only offers to remove automatically generated system or app-related data" and that a proprietary "Safety Database" of version- and app-specific rules prevents mistakes ([MacPaw: CleanMyMac safety and reliability](https://macpaw.com/support/cleanmymac/knowledgebase/cleanmymac-safety)) **[vendor; no technical detail published]**. MacPaw's Gemini 2 is the clearest reputable example of preselecting user files. When it scans Home, **Smart Selection marks duplicates in Downloads and Desktop but never in Documents**, never auto-selects "similar" files, and moves removals to Trash ([MacPaw: All about Smart Cleanup](https://macpaw.com/support/gemini/knowledgebase/gemini-2-smart-selection)) **[vendor]**. The older Gemini Classic kept the oldest copy and selected newer ones ([MacPaw: Gemini Classic automatic selection](https://macpaw.com/support/gemini-classic/knowledgebase/gemini-automatic-selection-work)) **[vendor]**.

DaisyDisk sits at the opposite end. It preselects nothing. Users drag items into a Collector, and "Files in the Collector remain intact until you click Delete." The Collector refuses `/System`, `/Library` and the home folder ([DaisyDisk guide: deleting files](https://daisydiskapp.com/guide/deleting-files)) **[vendor; snippet]**. DaisyDisk presents purgeable space (mostly snapshots) as a single macro item and can purge it only in the non-App Store edition ([DaisyDisk guide: purgeable space](https://daisydiskapp.com/guide/purgeable-space)) **[vendor]**. OnyX's current default checkboxes could not be confirmed from any primary source. A long-standing community guide frames its user-cache option as a troubleshooting step: "If an application is acting up, you may want to delete them; if not, don't use this command" ([Apple Community: Clearing caches with OnyX](https://discussions.apple.com/docs/DOC-2258)) **[forum; old]**.

Among open-source tools, Mole documents the most deliberate safety design, and it maps well onto a tiered recommender. `mo clean` covers "known-safe caches, logs, temporary files, developer artifacts, and leftovers." Every destructive command takes `--dry-run`, and a persistent whitelist halts the run if it cannot be read. "When Mole cannot prove an item is safe to change, it skips or refuses it." Build artifacts "with file activity in the last 7 days, or activity Mole cannot verify, are unselected by default." The uninstaller keeps "personal data, including settings and plugins" unless `--with-data` is passed, and even then it excludes browser profiles and App Group containers ([Mole README](https://raw.githubusercontent.com/tw93/Mole/main/README.md)). One caveat: Mole's `clean` deletes permanently, while its uninstaller uses Trash. mac-cleanup-py shows the opposite risk. Its "Default Modules" include `ios_backups` ("Removes iOS Device Backups") and Trash on all volumes, protected only by a CLI `--dry-run` ([mac-cleanup-py README](https://raw.githubusercontent.com/mac-cleanup/mac-cleanup-py/main/README.md)). Pearcleaner's README documents no selection defaults, and the project has been on hold since late 2025 ([Pearcleaner README](https://raw.githubusercontent.com/alienator88/Pearcleaner/main/README.md)).

Howard Oakley's position, consistent from 2016 to 2026, explains why the preselected tier should not be sold as a performance feature. Caches are "optional extras" that the `deleted` service purges when macOS needs space. Purging has "distinct trade-offs"; for example, deleting QuickLook caches makes Finder "much slower in Gallery mode," and the caches involved "aren't old, normally, they're the current ones in active use" ([Eclectic Light: Caches and purging in macOS Tahoe, 2026-09-02](https://eclecticlight.co/2026/09/02/caches-and-purging-in-macos-tahoe/)). His tests show that a cache flush "will invariably achieve considerably less" than the reported maximum and may not free significant space ([Eclectic Light: Will flushing caches free up disk space?](https://eclecticlight.co/2023/09/22/will-flushing-caches-free-up-disk-space/)). He says users "shouldn't need to worry about /private/var/folders, which is controlled by macOS," and he would rather developers documented their leftovers than users run heuristic cleaners ([Eclectic Light: Can we make cleaning up our Macs simpler?](https://eclecticlight.co/2025/01/26/last-week-on-my-mac-can-we-make-cleaning-up-our-macs-simpler/)). His 2016 test for any cleaner remains the best design checklist available. The tool must document exhaustively what each function removes, every function must be easy to reverse, and the tool must be updated promptly for each macOS release ([Eclectic Light: Why you shouldn't use cleaning or housekeeping apps](https://eclecticlight.co/2016/05/28/why-you-shouldnt-use-cleaning-or-housekeeping-apps/)).

The incident record is weak as evidence but consistent in where it points. Every reported loss is an anonymous forum post with unconfirmed cause. None involves cache cleaning. All involve user-content modules: CleanMyMac 2 flagging a Photos library as a "large & old file" ([Apple Community 7006767](https://discussions.apple.com/thread/7006767)) **[forum]**; a duplicate scan removing non-duplicate photos ([Apple Community 255229724](https://discussions.apple.com/thread/255229724)) **[forum]**; an uninstaller deleting "all my files and personal settings" ([Apple Community 5877946](https://discussions.apple.com/thread/5877946)) **[forum; snippet; ~2014]**; and a macOS 26.0 user losing Finder access to Documents and Downloads after removing "background items" ([Apple Community 256174524](https://discussions.apple.com/thread/256174524)) **[forum]**. The only formal action against a Mac cleaner, the 2014–2015 MacKeeper class action and its $2M settlement, concerned deceptive scare marketing, not data loss ([Network World](https://www.networkworld.com/article/942082/mackeeper-customers-can-file-a-claim-to-get-their-money-back.html)) **[snippet]**. Taken together, inflated "junk" totals are a legal and trust risk, and user-content features are where data actually gets lost.

## Developer caches are safe only through their owners' own commands

Developer caches are the one category where even cleaner vendors concede that real, recurring space can be recovered ([Mole: Do you need a Mac cleaner](https://mole.fit/blog/do-you-need-a-mac-cleaner)) **[vendor; snippet]**. The official guidance follows one pattern: **each ecosystem ships a prune command that respects its own locks, opt-outs and link structure, and several explicitly forbid touching the files directly.** That pattern creates a tension for an app whose safety model is "move to a restorable recovery folder."

Xcode is the largest case. An Apple Developer Forums answer endorsed by Quinn of Apple DTS says **"You can delete `DerivedData` at any time. It grows back as you load and build projects."** The same thread says you can delete any `iOS DeviceSupport` versions "that don't correspond to devices you actually use for debugging." It says `DocumentationCache` can go if `DocumentationIndex` goes with it. For CoreSimulator, "it's probably best to not monkey with that yourself but instead manage it via… Xcode or the `simctl` command-line tool," and in every case "make sure that Xcode is quit before you start deleting stuff behind its back" ([Apple Developer Forums 812408](https://developer.apple.com/forums/thread/812408)) **[forum; DTS-endorsed; single source]**. Apple's sanctioned simulator tools are `simctl delete unavailable` (devices "not supported by the current Xcode SDK") and `simctl runtime delete --unusable | --outdated | --notUsedSinceDays` with `--dry-run` **[local observation: `xcrun simctl help`, Xcode 27.2]**. Archives must never be preselected. dSYMs match a binary only by build UUID, and rebuilding the same source "with different Xcode versions or build settings" yields a non-matching UUID, so a deleted archive cannot be regenerated ([Apple Developer: Building your app to include debugging information](https://developer.apple.com/documentation/xcode/building-your-app-to-include-debugging-information)).

Package managers split into three groups. The first group consists of self-managing caches that are safe to prune through their CLI. Homebrew already prunes downloads older than 120 days and runs a full cleanup every 30 days. Its `brew cleanup` honours `HOMEBREW_NO_CLEANUP_FORMULAE`, which a raw delete of `~/Library/Caches/Homebrew` would bypass ([Homebrew Manpage](https://docs.brew.sh/Manpage)). Go's build cache "is safe for concurrent invocations" and trims itself ([cmd/go](https://pkg.go.dev/cmd/go)). The Go module cache is written read-only on purpose, "making the cache difficult to delete with commands like `rm -rf`," so the supported route is `go clean -modcache` ([Go Modules Reference](https://go.dev/ref/mod)). pip's `pip cache purge` clears wheel and HTTP caches whose structure "may change between any two versions of pip" ([pip: Caching](https://pip.pypa.io/en/stable/topics/caching/)). npm's cache "is strictly a cache," and clearing it needs `--force` ([npm docs: npm-cache](https://docs.npmjs.com/cli/v10/commands/npm-cache)). Cargo says "you can always remove any part of the cache and Cargo will do its best to restore" it, and since Rust 1.88 it garbage-collects unused downloads after three months ([Cargo Book: Cargo Home](https://doc.rust-lang.org/cargo/guide/cargo-home.html); [Rust 1.88.0](https://blog.rust-lang.org/2025/06/26/Rust-1.88.0/)). Cypress's `cypress cache prune` keeps the binary in use ([Cypress: Advanced installation](https://docs.cypress.io/app/references/advanced-installation)). Playwright already deletes browser versions no client uses, so whatever remains in `~/Library/Caches/ms-playwright` is probably in use ([Playwright: Browsers](https://playwright.dev/docs/browsers)).

The second group consists of caches where a direct move is unsupported or harmful. uv states that **"it's _never_ safe to modify the cache directly (e.g., by removing a file or directory)"** and that `uv cache prune`/`clean` take a lock that other uv processes respect ([uv: Cache](https://docs.astral.sh/uv/concepts/cache/)). pnpm hard-links its global store into every project's `node_modules` and recommends `pnpm store prune`, which "is not harmful and has no side effects on your projects" ([pnpm: store](https://pnpm.io/cli/store); [pnpm FAQ](https://pnpm.io/faq)). conda's `--force-pkgs-dirs` "will break environments with packages installed using symlinks back to the package cache," and `--all` deliberately excludes it ([conda clean](https://docs.conda.io/projects/conda/en/stable/commands/clean.html)). Gradle cleans `~/.gradle/caches` itself (30-day downloads, 7-day build cache) when the daemon stops. It relies on cross-process file locks and does not document manual deletion ([Gradle: Directory layout](https://docs.gradle.org/current/userguide/directory_layout.html); [Gradle: Dependency caching](https://docs.gradle.org/current/userguide/dependency_caching.html)).

The third group consists of locations that look like caches but hold real data. Maven's `~/.m2/repository` holds "temporary build artifacts that you have not yet released," meaning `mvn install` outputs that may exist nowhere else ([Maven: Introduction to Repositories](https://maven.apache.org/guides/introduction/introduction-to-repositories.html)) **[snippet; direct fetch failed]**. A Yarn Berry project's `.yarn/cache` "can then be added to Git" for zero-installs ([Yarn: Caching](https://yarnpkg.com/features/caching)). Cargo's `bin/` and `.crates*.json` record installed tools ("Do NOT edit by hand!") ([Cargo Book: Cargo Home](https://doc.rust-lang.org/cargo/guide/cargo-home.html)). Docker Desktop keeps every image, container and volume in one `Docker.raw` inside `~/Library/Containers/com.docker.docker`. Docker warns: "Do not move the file directly in Finder." Space returns only through `docker system prune`, which by default does not remove volumes, to prevent "important data from being deleted" ([Docker Desktop Mac FAQ](https://docs.docker.com/desktop/troubleshoot-and-support/faqs/macfaqs/); [docker system prune](https://docs.docker.com/reference/cli/docker/system/prune/)).

Project build outputs (`node_modules`, Cargo `target`, Gradle `build` and `.gradle`) are documented as generated output ([Cargo Book: cargo clean](https://doc.rust-lang.org/cargo/commands/cargo-clean.html); [Gradle: Directory layout](https://docs.gradle.org/current/userguide/directory_layout.html)). They are rebuildable only when a lockfile exists and the network is available. Mole's rule of unselecting anything touched in the last seven days, and skipping Git-tracked content, is the best documented guard ([Mole README](https://raw.githubusercontent.com/tw93/Mole/main/README.md)). No npm, pnpm or Yarn document offers guidance on deleting `node_modules` from inactive projects, so the remaining safeguards are design inference. Those safeguards are: require a lockfile, require a matching manifest, and skip directories open in a running dev server.

The design consequence is that owner-command prunes delete permanently. They cannot go through the recovery folder, and for uv, Go's module cache and pnpm, moving the directory is exactly the operation the owners warn against. The defensible split is to stage pure cache folders (DerivedData, npm `_cacache`, `~/Library/Caches/<third-party>`) in the recovery folder, and to run owner commands as a separate "permanent but re-downloadable" action. That action should be preselected only where the tool's documentation calls it harmless, it should run as the user and never as root ([Homebrew Manpage](https://docs.brew.sh/Manpage)), and it should run only when no process of that toolchain is running.

## SIP, TCC and sync engines put whole subtrees off-limits

Some paths are off-limits because macOS forbids writing to them; others because a write would destroy data or spread to other devices. Apple's SIP page lists `/System`, `/usr`, `/bin`, `/sbin`, `/var` and the preinstalled apps as protected. Third parties may still write to `/Applications`, `/Library` and `/usr/local` ([Apple Support 102149: About System Integrity Protection](https://support.apple.com/102149)). Since macOS 11, system content also sits on a Signed System Volume whose kernel mechanism "rejects any data… without a valid cryptographic signature from Apple" ([Apple Platform Security: Signed system volume security](https://support.apple.com/guide/security/secd698747c9/web)) **[snippet]**. Stripping localisations from macOS itself, the classic Monolingual feature, is therefore impossible. Doing it to third-party apps risks a strict code-signature failure: Apple DTS describes `codesign --strict` reporting "a sealed resource is missing or invalid" ([Apple Developer Forums 706379](https://developer.apple.com/forums/thread/706379)) **[forum; snippet]**. An older developer reading holds that missing translations are tolerated ([furbo.org, 2015](https://furbo.org/?p=1818)) **[single source; old]**. The conflict is unresolved for macOS 13–26, which is reason enough not to ship the feature.

The more consequential protections cover user-domain data. Apple says app data containers "offer System Integrity Protection." In macOS 15 and later, app group containers do too, and any app outside the group that accesses them prompts the user ([Apple Developer: Protecting local app data using containers on macOS](https://developer.apple.com/documentation/xcode/protecting-local-app-data-using-containers)). Oakley's verdict: "If in doubt, leave Containers well alone." A document saved inside a container "will then be gone for ever" if the container is deleted, and macOS keeps containers after uninstall so that a reinstall resumes where the user left off ([Eclectic Light: What are all those Containers?](https://eclecticlight.co/2024/08/05/what-are-all-those-containers/)). One non-Apple site claims that macOS 27 denies cross-developer container access outright, without a prompt ([macos-tahoe.com](https://macos-tahoe.com/blog/macos-27-app-data-containers-access-denied-operation-not-permitted-fix-2026/)) **[single source; unverified]**. TCC also guards `~/Documents`, `~/Downloads`, `~/Desktop`, iCloud Drive, FileProvider storage, removable, network and Time Machine volumes, as of Oakley's tests on macOS 26.4 ([Eclectic Light: Privacy: protected folders](https://eclecticlight.co/2026/04/07/privacy-protected-folders/)). There, "You can have full Unix-style permissions to read and write a file, but privacy protection can still block that" ([Eclectic Light: Privacy: How locations are protected](https://eclecticlight.co/2026/04/20/privacy-how-locations-are-protected/)). For a tool, a permission-denied error should mean "skip and report as protected by macOS," never "retry with more privilege."

Sync engines turn local deletes into remote ones. `~/Library/Caches/com.apple.bird` is the iCloud Drive daemon's working store. Users who deleted it together with CloudDocs reported that "nothing is working," while toggling iCloud Drive off and on emptied it safely ([Apple Community 255888674](https://discussions.apple.com/thread/255888674)) **[forum; snippet]**. Deleting inside `~/Library/Mobile Documents` or `~/Library/CloudStorage` "can propagate" to every device ([Mole: What Mac cleaners should never delete](https://mole.fit/blog/what-mac-cleaners-should-never-delete.md)) **[vendor]**. One user disabled iCloud Keychain, deleted items locally and re-enabled sync, and the emptied state wiped the iPhone's logins too ([Apple Community 252645764](https://discussions.apple.com/thread/252645764)) **[forum; snippet]**. The TCC databases (`~/Library/Application Support/com.apple.TCC/TCC.db` and its `/Library` counterpart) are a "nuclear option" that Oakley would touch only "when all else fails and you're desperate" ([Eclectic Light: The woes of TCC](https://eclecticlight.co/2023/02/09/should-you-reset-its-database-or-delete-it-the-woes-of-tcc/)). Rebuilding a Mail mailbox deletes local copies and re-downloads from the server, so messages stored only "On My Mac" have no server copy to come back from ([MacPaw: rebuild mailbox](https://macpaw.com/how-to/rebuild-mailbox-mac)) **[vendor; snippet]**.

Two system-managed areas look tempting but should be left to macOS. `/private/var/folders` holds live per-user caches for "lots of processes… not just Xcode" ([lists.apple.com xcode-users, 2008](https://lists.apple.com/archives/xcode-users/2008/Jul/msg00347.html)) **[snippet; old]**. Clearing it is known both to fix Dock icons and to cause boot and QuickLook breakage ([Jamf Nation](https://community.jamf.com/t5/jamf-pro/run-away-var-folders/m-p/37435); [Apple Community 6619152](https://discussions.apple.com/thread/6619152)) **[forum; snippet]**. The Apple-aligned alternative is a restart or safe-mode boot. Local snapshots are the second area. Oakley found that Finder and Storage misreport purgeable space and that macOS sometimes "refused to purge" a large snapshot ([Eclectic Light: Aren't snapshots purgeable?](https://eclecticlight.co/2026/08/24/arent-snapshots-purgeable/)). He advises that "you can safely delete all except the most recent snapshot, when each snapshot is accompanied by a backup" ([Eclectic Light: Which snapshots could you delete?](https://eclecticlight.co/2026/02/02/which-snapshots-could-you-delete/)), and recommends `tmutil thinlocalsnapshots` so that macOS chooses what to remove ([Eclectic Light: Take control of snapshots](https://eclecticlight.co/2026/09/09/take-control-of-snapshots/)) **[snippet]**.

## Root buys almost nothing, and a password field copies the stealers

Nearly all space worth reclaiming safely sits in locations the user already owns. On the research machine, the privileged locations were small or pointless targets **[local observation: `ls -ldO`, macOS 26.6.2, SIP on]**. `/Library/Caches` is sticky and world-writable, with entries owned by root or daemon accounts, and listing several `com.apple.*` entries failed with "Operation not permitted" even before deletion was attempted. `/Library/Logs` and `/private/var/log` are `root wheel 755`. `/Library/Logs/DiagnosticReports` is group-writable by `_analyticsusers`, which the admin user belonged to. `/private/var/db/diagnostics` (the unified log) is root-deletable only. `/Library/Updates` carries the SIP `restricted` flag, so even root cannot delete it. Even MacPaw's blog advises that system caches in `/Library/Caches` are "best to leave… alone unless you're troubleshooting something specific" ([CleanMyMac blog: clear cache](https://cleanmymac.com/blog/clear-cache-mac)) **[vendor]**. The one privileged reclaim of real size is snapshot thinning, and the `tmutil` man page says only that "Several, but not all, verbs require root and Full Disk Access" without naming which **[local observation: `man tmutil`]**. Community guides run snapshot deletion with `sudo` ([Apple Community 255461563](https://discussions.apple.com/thread/255461563)) **[forum]**. Full Disk Access is a separate axis from root. A CLI inherits whatever TCC grants Terminal holds, so asking users to grant Terminal Full Disk Access widens access for everything they run in it. That is an inference from Oakley's account of the TCC check order ([Eclectic Light: Privacy: How locations are protected](https://eclecticlight.co/2026/04/20/privacy-how-locations-are-protected/)) and the `tmutil` man page.

Apple DTS's canonical post on BSD privilege escalation, first posted in 2022 and revised through March 2025, settles which mechanisms are acceptable ([Apple Developer Forums 708765](https://developer.apple.com/forums/thread/708765)) **[forum; DTS-authored]**. Its rulings: "Do not use a setuid-root executable. Ever." `AuthorizationExecuteWithPrivileges` has been deprecated since 10.7: "Do not use it in a widely distributed product." `sudo`, `authopen` and `osascript` "are not appropriate to use as API." AppleScript `with administrator privileges` is acceptable only for "an ad hoc solution to distribute to a limited audience." `SMJobBless` has been deprecated since macOS 13, and `SMAppService` is the recommended route for ongoing privileges. An installer package is "by far the easiest solution" for install-time privileges. `SMJobSubmit` is deprecated but still used by Sparkle, so "unlikely to break without warning." `SMAppService` registers a root daemon from inside a signed app bundle and needs user approval in Login Items ([Csaba Fitzl: The SMAppService API](https://theevilbit.github.io/posts/smappservice); [Apple Developer Forums 721919](https://developer.apple.com/forums/thread/721919)). That fits a GUI app with recurring privileged work. It fits poorly for a CLI/TUI that needs root once a month. One report says `smd` rejects previously working `SMJobBless` installs on macOS 26.4.1 ([exelban/stats PR 3194 mirror](https://github.kakarurec.workers.dev/exelban/stats/pull/3194)) **[single source; unverified]**.

For a terminal tool, the native mechanism is `sudo` itself, invoked on the user's real TTY with a fixed, reviewed command line, so that macOS's PAM stack handles authentication. Since Sonoma, `/etc/pam.d/sudo` includes `sudo_local`. Uncommenting `pam_tid.so` in a copy of Apple's template enables Touch ID for sudo, and the setting survives updates ([Six Colors, 2023](https://sixcolors.com/post/2023/08/in-macos-sonoma-touch-id-for-sudo-can-survive-updates/)). This was confirmed on macOS 26.6.2 **[local observation: `/etc/pam.d/sudo`]**. It works only at the local console, not over SSH. Two points remain unsourced and need testing: the sudo timestamp timeout, and Touch ID inside tmux.

Collecting the password in the tool's own form is the wrong design on three counts. First, it holds a credential in process memory and pipes it to `sudo -S`. That matches CWE-256 ("stores a password in plaintext within resources such as memory") and CWE-522 ([MITRE CWE-256](https://cwe.mitre.org/data/definitions/256.html); [MITRE CWE-522](https://cwe.mitre.org/data/definitions/522.html)). The mapping of `sudo -S` to these CWEs is an inference, not a published ruling. Second, it reproduces the leading macOS stealer technique. ClickLock (2026) opens a fake `osascript` password dialog, validates the entry with `dscl -authonly`, and kills apps in a loop until the user complies ([Group-IB: ClickLock stealer](https://group-ib.com/blog/clicklock-stealer-macos-malware); [The Hacker News](https://thehackernews.com/2026/07/new-clicklock-macos-stealer-kills-apps.html)). SHub Reaper re-prompts until the password is correct ([SentinelOne](https://sentinelone.com/blog/shub-reaper-macos-stealer-spoofs-apple-google-and-microsoft-in-a-single-attack-chain)). Defenders now publish rules to block such prompts ([North Pole Security](https://northpole.security/cookbook/block-fake-password-prompts)). A cleaner that asks for the password trains users into the habit that endpoint tools are trying to break. Third, the cleaner industry's own root code has a poor record. Cisco Talos found that CleanMyMac X 4.04's helper exposed root functions, including `removeDiagnosticLogs` and `moveItemAtPath`, with "no validation of the calling application" ([Talos TALOS-2018-0709](https://talosintelligence.com/vulnerability_reports/TALOS-2018-0709); [TALOS-2018-0718](https://talosintelligence.com/vulnerability_reports/TALOS-2018-0718)). A follow-on helper escalation was assigned CVE-2019-5011 ([NVD](https://nvd.nist.gov/vuln/detail/cve-2019-5011)). Patrick Wardle showed that `AuthorizationExecuteWithPrivileges` leaked a reusable authorization through a world-readable temp file from OS X 10.4 until 10.13.1 ([Objective-See blog 0x55](https://objective-see.org/blog/blog_0x55.html)). The lesson from these CVEs is that the dangerous artefact is a generic root primitive of the form "delete this path." Oakley made the same criticism in 2026 of an unnamed cleaner's "old scripted workaround to perform privileged operations, rather than doing it properly with a privileged helper app" ([Eclectic Light: Storage crisis management](https://eclecticlight.co/2026/09/06/last-week-on-my-mac-storage-crisis-management/)).

## Duplicates on APFS can free zero bytes or delete the cloud copy

Byte-identical files on APFS often share storage, so the size a duplicate finder reports is frequently not the space deletion would free. A Finder duplicate is a clone: it has its own inode but "shares the same data blocks and extended attributes." Deleting one clone leaves those blocks in place because "they're still required by the other clone," and snapshot-held blocks likewise stay ([Eclectic Light: APFS: Files and clones](https://eclecticlight.co/2024/03/20/apfs-files-and-clones/)). Finder's "On Disk" figure ignores this. In Oakley's test, a cloned 107 GB VM showed 54.57 GB on disk, while Disk Utility showed only 0.74 GB actually added ([Eclectic Light: When the Finder's size 'on disk' is misleading](https://eclecticlight.co/2026/09/05/when-the-finders-size-on-disk-is-misleading/)). Apple's `getattrlist(2)` provides the correct figures. `ATTR_CMNEXT_PRIVATESIZE` is "the number of bytes… which would be freed immediately if the file were deleted." `ATTR_CMNEXT_CLONEID` is "useful for finding which files are pure clones of each other." The flags `EF_MAY_SHARE_BLOCKS` and `EF_SHARES_ALL_BLOCKS` mark partial and full clones ([getattrlist(2) mirror](https://keith.github.io/xcode-man-pages/getattrlist.2.html); also **[local observation: `man getattrlist`]**). On one point the sources disagree: Oakley wrote that "there's no direct way to tell which are clones of one another," while Apple's documented `CLONEID` attribute does exactly that. The likely explanation is that Oakley did not cover the attribute. PRIVATESIZE per file also undercounts when every member of a clone group is deleted, so groups must be handled by CLONEID.

Hard links behave even more simply: one inode, many paths, and zero bytes freed while any link survives. jdupes treats linked files "as non-duplicates for safety" ([jdupes README](https://codeberg.org/jbruchon/jdupes)). fclones drops same-inode files ([fclones README](https://github.com/pkolaczk/fclones)). dupeGuru can ignore same-inode files on macOS ([dupeGuru preferences](https://dupeguru.voltaicideas.net/help/en/preferences.html)). rmlint is the outlier, treating hard links as duplicates by default ([rmlint(1)](https://rmlint.readthedocs.io/en/latest/rmlint.1.html)). pnpm's store makes this concrete for developers, because every `node_modules` file is a hard link into it ([pnpm FAQ](https://pnpm.io/faq)).

iCloud Drive and File Provider make scanning itself hazardous. Since Sonoma, evicted files are dataless rather than `.icloud` stubs: they have "the same file size as fully downloaded files" but no local extents. Apple's advice, relayed by Oakley, is to check `SF_DATALESS` in `st_flags` ([Eclectic Light: macOS Sonoma has changed iCloud Drive radically](https://eclecticlight.co/2023/10/25/macos-sonoma-has-changed-icloud-drive-radically/)). The flag's value is `0x40000000` **[local observation: `sys/stat.h`]**. Dropbox, Google Drive, OneDrive and Box use the same mechanism, and reading a placeholder "asks the provider to download the content again" ([Arq 7: Backing up dataless files](https://arqbackup.com/documentation/arq7/English.lproj/datalessFiles.html)) **[vendor]**. A naive hashing pass would therefore download the user's entire cloud library, and deleting a placeholder frees no local space while deleting the file everywhere. Apple's TN3150 tells apps to "avoid unnecessarily materializing dataless files." It also notes that even `stat` and `getattrlist` materialize dataless intermediate folders ([TN3150](https://developer.apple.com/documentation/technotes/tn3150-getting-ready-for-data-less-files), quoted via [Michael Tsai](https://mjtsai.com/blog/2023/05/11/getting-ready-for-dataless-files)) **[secondary quote; Apple page not fetched]**. `setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, …, IOPOL_MATERIALIZE_DATALESS_FILES_OFF)` disables materialization for the process **[local observation: `man setiopolicy_np`, `sys/resource.h`]**. The man page claims materialization is off by default, which conflicts with observed behaviour, so the tool should set the policy explicitly. The error returned under the policy is unconfirmed: one forum report cites `ETIMEDOUT` ([Apple Developer Forums 825820](https://developer.apple.com/forums/thread/825820)) **[forum; single source]**.

Identical data forks also do not make identical files on macOS. Finder tags, download provenance (`kMDItemWhereFroms`), quarantine, FinderInfo and resource forks live in extended attributes, and these can differ between copies with the same bytes ([Eclectic Light: The secret life of the xattr](https://eclecticlight.co/2026/04/24/the-secret-life-of-the-xattr/)). None of the open-source duplicate finders reviewed documents comparing them. Which copy to keep has no single standard. dupeGuru never marks a reference-folder file and otherwise keeps the biggest ([dupeGuru: Results](https://dupeguru.voltaicideas.net/help/en/results.html)). rmlint ranks by path order, then outside hard links, then oldest mtime ([rmlint(1)](https://rmlint.readthedocs.io/en/latest/rmlint.1.html)). Czkawka protects reference paths from "any automatic action" ([Czkawka Instruction](https://github.com/qarmin/czkawka/blob/master/instructions/Instruction.md)). Gemini 2 selects by location. On safety, jdupes warns that skipping its final byte comparison "may delete non-duplicates," and calls disabling change checks a TOCTTOU vulnerability ([jdupes README](https://codeberg.org/jbruchon/jdupes)). rmlint's `-p` re-checks each duplicate against the original before deletion ([rmlint(1)](https://rmlint.readthedocs.io/en/latest/rmlint.1.html)). No source documents any rule about Photos libraries or app bundles. Excluding package contents is a design necessity that rests on inference, supported by the forum loss reports involving Photos libraries.

## Five tiers for the recommendation engine

Every tier assumes some common gates, which follow from the evidence above. The owning app or toolchain must not be running, checked again just before acting. Owner-command actions run as the user. Size is reported as PRIVATESIZE or allocated bytes, not logical size, and purgeable bytes are labelled as already available. Every staged move records enough to restore it. Moving items to a recovery folder on the same volume reclaims nothing until that folder is purged, so the UI should separate "staged" from "freed." That last point is a design inference.

The ranking of elevation mechanisms follows Apple DTS ([Forums 708765](https://developer.apple.com/forums/thread/708765)) and the CVE history. Best is to run unprivileged and print the exact command (`sudo tmutil thinlocalsnapshots / …`) for the user to run. Next is to exec `sudo` with a fixed argv on the inherited TTY, so that sudo and PAM prompt, with Touch ID available through `sudo_local` ([Six Colors](https://sixcolors.com/post/2023/08/in-macos-sonoma-touch-id-for-sudo-can-survive-updates/)). For a signed GUI bundle with recurring needs, use `SMAppService` with a helper that accepts only fixed targets, validates its caller, and resolves paths with no-follow semantics, which are the lessons of [TALOS-2018-0709](https://talosintelligence.com/vulnerability_reports/TALOS-2018-0709) and [Reguła's XPC research](https://www.securing.pl/en/presentation/abusing-securing-xpc-in-macos-apps/). Never acceptable: an in-app password field, `sudo -S` piping, `AuthorizationExecuteWithPrivileges`, setuid-root, a persistent root helper for an occasional task, or `osascript … with administrator privileges` in a distributed product.

## Conclusion

The evidence points to a shift in what a cleanup app is for. The space that is both safe to preselect and large is almost entirely developer build products and package caches. The ecosystems that own those caches each say how to clear them, and several say outright not to delete the files directly. So the tool's main value is knowing the owners' rules and their running-process conditions, not finding "junk" in `~/Library`. A restorable recovery folder is a genuine advance on what most cleaners do, because it meets Oakley's reversibility test. It also creates two classes of action the UI must show honestly. Staged moves can be undone but free nothing until purged. Owner-command prunes free space immediately but cannot be undone, and they are acceptable only where the owner calls them harmless.

Evidence is weakest exactly where cleaners claim the most. MacPaw's Safety Database is undocumented, OnyX's defaults are unknown, Saved Application State has no Apple semantics, and every data-loss incident is an unverified forum post. That argues for publishing the tool's own rule table, with a reason and source for each path, as the product's trust signal. It also argues for treating anything Apple manages itself (snapshots, `/private/var/folders`, purgeable files, iCloud state) as something to explain and hand off to Apple's controls, not something to "clean." Several points need confirmation on target machines before shipping: whether `tmutil` thinning needs root on each macOS version, how the dataless-materialization error code and default policy behave, whether `SMJobBless` breaks on 26.4+, and whether macOS 27 tightens container access.
